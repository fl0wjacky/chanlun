# ③ 修正：续扫在「尾端点被换」时会 stale —— 非纯追加一律整段重算

## 结论一句话

原三路同步里「守卫 2 尾端点被换 ⇒ 只重推最后一笔、续扫」是**错的**。换的是最后那根笔，
会翻动 `openingOverlaps` 倒数几格（i-2..i）的判词，而续扫的 `i` 只增不回，已经跳过去的
位置不会再回来问 ⇒ 缓存段 stale。修正：**只有「纯追加」走增量续扫，其余一切改动
（尾端点被换 / 缩水 / 跳变 / 深处回改）一律整段重算。**

## 根因（skip-flip）

`zec_1h` @bar 150-158：`seq=[8,34,92,109]`，`openingOverlaps(pens,0)=假` ⇒ 续扫把 i 从 0 跳到 1。
@bar 159：最后一格端点 109→118（尾端点被换，守卫 2），这根笔一换，`openingOverlaps(pens,0)`
从假翻成真。但 i 已经 =1，位置 0 再没被问过 —— 整段重算会给出一条 live 段 {0,2}，增量给空。

关键不在「pens 同步漏没漏」——pens 是对的（`pen-sync-deepfix-probe.py` 全程 0 漏）。错在
**段扫描状态 (zSegI, zSegBorn, zSegs)**：它押「跳过去的位置永远不用再问」，这条只在**纯追加**
时成立（追加不动旧前缀），一旦笔被**改**（哪怕只改最后一根），就不成立。

`fix_start` 能回改 5 笔深（zec15@3738 深 5、zec_2h@206 深 4，实测），比「endPen ≤ M-4」这个
保护边界还深 —— 所以「zSeq 只动最后两格」那套论证本来就站不住。现在不押它了，押的是
「非纯追加一律重算」。

## 修正（pine 侧，zSegStep）

三路收成两路：

```
if 变了(笔数 or 尾三格签名)
    if 纯追加（多一笔、旧尾巴签名不动）
        pens.push(最后一笔)          // 旧前缀没动，续扫安全
    else
        清空 pens + segs，segI/segBorn 归零，从头补摊平   // 含尾端点被换
    sig 更新
续扫（从 segI/segBorn 起，镜像 buildSegments 内层）
```

## 验证

- `pen-sync-deepfix-probe.py`：三路守卫维护的 pens == 整条重摊平，**88316 根 0 漏**（真实 36921
  + 随机 51395），回改最深 zec15@3738 深 5。
- `seg-sync-deepfix-probe.py`（新增）：把 zSegStep **整条**搬成 Python，喂真实 `Guarded` 的 seq，
  逐根跟 `build_segments` 对账。修正前 zec_1h@159 / btc_4h@1602 / zec15@3270 / 随机 #17 都红；
  **修正后 37364 根 0 分歧**（真实 21721 + 随机 15643）。

两个尺子合起来 = ① 笔同步不漏 + ② 段续扫 == 整段，在真实 fix_start 深处回改下逐根成立。
