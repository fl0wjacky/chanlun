# ③ 「只从最后一个已确认段末笔之后重扫」不成立 —— partial 提案被实测否决

## Nova 的提案

「非纯追加一律整段重算」里，尾端点被换是最常见的（最后一笔延伸几乎每几根来一次）。
既然已确认段之前的位置不会再被翻动，能不能**只从最后一个已确认段的末笔之后重扫**，
不必从 0 开始？既对又省。

## 实测：不对，分歧了

`seg-reset-cost-probe.py`（old / full / partial 三支同跑、逐根 vs `build_segments`）：

- **btc_4h@1602**：partial 分歧 391 处（首处 @1602）。
- **zec_1h@1433**：partial 分歧 800 处（首处 @1433）。
- full 全程 0 分歧（后面全量再验）。

## 根因：已确认段本身不稳，不是扫描游标的事

zec_1h@1433 现场（尾端点被换，penCount=83）：

```
整段 build_segments:  {0,8} {9,29} {30,50} {51,65}  + live {66,82}
partial:              {0,8} {9,29} {30,50} {51,65} {66,72}(case2) {73,79}(case1) + live {80,82}
```

partial 早先已把 `{66,72}` 和 `{73,79}` 确认下来并留着；但整段重算在这根 bar 上**不再确认**这两段，
`{66,82}` 整段是一条 live（未确认）。关键：`{73,79}` 的 endPen=79 ≤ M-4=80，看着在「已确认段保护边界」
内，可它是 **case-1** —— 破位笔由 `_case_at` 里 `for r in range(k+2, len(pens))` 向前扫出，扫到
pens[81]、pens[82]（尾巴）；尾笔一换，破位笔就变，这段就撤销。`{66,72}` 的 **case-2** 同理，
`_reverse_scan` 读反向分型也读到尾巴。

一句话：**「已确认段之前的位置不会再被翻动」是假的 —— 确认这件事本身就押在尾巴上。**
case-1 的破位笔、case-2 的反向分型，都要读段 endPen 之后的笔直到当前尾巴；尾巴一动，前面
已确认的段照样被翻。所以「从最后已确认段末笔之后重扫」救不了 —— 那个「最后已确认段」自己
就是 stale 的。

## 结论

- 非纯追加（尾换 / 缩水 / 跳变 / 深处回改）一律整段重算，**收不回**「只重扫尾巴」那支。
- 代价可接受：O(n) 根比例 3.8%~7.1%（zec15 全量 6.3%），93%+ 是 O(1)（无事 88%、纯追加 5.6%）；
  单根最坏 zec_1h 294 笔、zec15 全量 1135 笔。超时风险没回来。
