# ③ 探针：featDir=B 的前缀稳定性破了 —— `_reverse_scan` 反向分型确认非单调

## 结论一句话

`build_segments` 对 **featDir=A（默认）是前缀单调的**（9 份全稳定，增量=整段逐字节相同）；
对 **featDir=B（全程按线段方向）不是**：zec15 上第 499 笔起，增量（缓存已确认前缀 + 只重算活尾巴）与整段**分道扬镳**。

根因是 `_reverse_scan` 的第二种情况反向分型确认**非单调**：反向分型先形成（n=495）又被后一根笔包含破坏（n=499）。这不是我的尺子错 —— mode A 每个前缀全绿，证明 `feed` 逐行复刻了 `build_segments`；是**引擎本身在 mode B 上非单调**。

## 证据

**① 前缀稳定探针（mode A 默认）** —— `notes/pine-seg-prefix-stability.py`，exit 0：
```
aaplusdt_1h/2h/30m/4h、btc_4h、zec15(1135笔)、zec_1h/2h/4h  ✓ 全程稳定
```

**② 增量参照（mode A）** —— `notes/pine-incremental-seg.py`，9 份 × 每前缀 × 两种 mode：
```
mode=A 全绿（zec15 前缀 1133 个全 ✓）
mode=B 全绿，唯独 zec15 @k=499 分歧 3 处
```

**③ 机制** —— `_reverse_scan(pens[:n], 486, 'down', B)` 的 `ok`：
```
n=487..494  ok=False   分型还没走出来
n=495..498  ok=True    分型形成 ⇒ _case_at 返回 case=2 ⇒ 确认 {472,486,case2}
n=499       ok=False   第 498 笔包含合并，把最后那个分型破坏掉 ⇒ 整段重算不再确认
```
翻转方向才是关键：

| 翻转方向 | 语义 | 对前缀稳定性的影响 |
|---|---|---|
| False→True | 分型终于形成 | **无害**：确认集合只增不减，前缀稳定 |
| True→False | 已形成的分型被包含破坏 | **致命**：已确认的段被撤销，前缀不稳定 |

zec15 全量 case-2 段：mode A **22 段、0 次 True→False**；mode B **21 段、1 次 True→False**（就是 ep=486 这一处）。

**④ 最终影响（n=1135）**：
```
mode B  batch segs=129   incremental segs=131
confirmed 前缀：batch 128 / incremental 130，mismatch 11 处
第一处 mismatch @confirmed j=119：batch {1037,1057,case1}  incremental {1037,1039,case2}
```
一处 {472,486} 的误确认，把后面整条链都带偏了（增量锁定后 i 从 487 走，batch 停在 472 重新判）。

## 为什么 mode A 没踩到、mode B 踩到了

`_feature_std` 的合并方向：
- mode A：`go_up = up if len(m) < 2 else (a.h > m[-2].h)` —— 后面按「最后两根」定方向；
- mode B：`go_up = up` —— **全程按线段方向**。

合并方向不同 ⇒ 第 498 笔在 mode B 下把反向分型合并吸收、在 mode A 下没有。**踩不踩得到是数据 + 方向口径决定的**，不是结构性保证：mode A 现在 9 份全稳定，不代表永远稳定。

## 需要决策（Nova + 小栋）

这是**语义问题，不是纯工程问题**，我不能单方面定：

**问题**：反向分型一旦形成，后一根笔「包含合并」把它破坏掉，算不算撤销确认？
- 文档 `_reverse_scan` 写的是「反向序列没出分型之前同样是待定」—— 言下之意**出了分型就该确认**（单调读法）。
- 但实现是每次把整条尾巴重算一遍，所以「已形成」会退化成「没形成」（True→False）。

**两条路**：
1. **判它是 bug，修 `_reverse_scan` 单调化**（分型形成即锁定，不再被后笔撤销）⇒ 两个 mode 都变前缀稳定 ⇒ ③ 的「缓存已确认前缀」增量对 A/B 都成立。但这是**改 engine 判据**，得小栋点头 + 重跑 spec 探针 + 走完整回归。
2. **判它是对**（分型本就可在形成后被包含破坏，批处理全量重算的答案才是「真」）⇒ ③ 增量不能无脑缓存已确认前缀。要么 featDir=A 走增量、B 保持整段重算（两条路径，丑）；要么增量只把「反向分型尚未锁定（价格还没越过 pivot）」的那段当活段、**不跨过它缓存**，每根从当前活段的起点重扫。

我倾向先让小栋回答「反向分型形成后该不该被撤销」，这是根子。定了再选实现。

## 顺带：这把尺子能跑通了

`notes/pine-incremental-seg.py` 本身是对的（mode A 全绿证明它逐行复刻，mode B 的红是引擎真红）。
它连同 `pine-seg-prefix-stability.py` 就是 ③ 的「引擎对照」参照 —— 现在卡在**引擎侧语义**，不是卡在移植。

## 结局（Nova 裁决 + 我独立验证）

**决定：不改引擎、不问小栋，③ 走「A 增量、B 整段」。**

Nova 的推理（我核过、成立）：mode A 的合并方向随「最后两个元素」走（同 K 线），顶分型要求第三元素比第二低 ⇒ 局部方向必然朝下 ⇒ 合并只取低 ⇒ 第三元素只会更低 ⇒ **分型撤不掉**，这是**结构性质**，不是数据碰巧。mode B 全程按线段方向合并：朝上取高 ⇒ 第三元素可能被抬过第二 ⇒ 已形成的分型就没了。

**独立验证（2000 条随机笔序列，统计 `_reverse_scan` 反向分型 `ok` 翻转）**：
```
mode A：True→False 撤销 0 次，False→True 形成 317 次   ← 撤销=0，坐实结构稳定
mode B：True→False 撤销 27 次，False→True 形成 282 次  ← 撤销真实存在
```

**实现结论**：③ 参照定稿 = A 走 `IncSegments`（缓存已确认前缀 + 重算活尾巴），B 直接 `build_segments` 整段。
`featDir` 默认 A；用户显式选 B 才吃整段重算，可接受。等 Iris 配色合完、文件回我手上再动 pine。
